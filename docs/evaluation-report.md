## 1. Executive summary (~150 words)

The core learning loop is genuinely implemented end-to-end: Space → Project → PDF upload → Celery ingest (chunk, Gemini 768-d embed, pgvector) → project-scoped RAG Tutor with citations and refusal handling → batch adaptive Quiz with strict LLM grading → 70/30 mastery blend with append-only history → growth analytics → inline recommendations → admin operations center. Data isolation is enforced per endpoint via ownership dependencies and project-filtered retrieval. AI observability (metered tokens/cost/latency) and evaluation dashboards are honest about what is not instrumented. The main gaps are architectural simplifications, not missing screens: recommendations are rule-based and never persisted (no table), adaptivity is weakest-first batch rather than per-question, there is no streaming/caching/pagination, tests cover only pure growth math, and minor hardening gaps (filename sanitization, default admin creds, 7-day JWT). Score 79% with no CRITICAL unsatisfied.

## 3. Core learning loop walkthrough (~500 words)

Create Space → Project works end-to-end: `spaces.py:16-40` and `projects.py:16-59` enforce per-user ownership, and the Spaces page (`Spaces.jsx:44-131`) handles create/edit/delete with confirmation modals. Project creation captures name plus `learning_goal` (`Spaces.jsx:97-100`), which later feeds quiz generation (`quiz_flat.py:114-138`). Upload accepts PDFs only with both hash and filename duplicate guards (`materials.py:106-151`), writes in 1 MB chunks, records `queued`, and dispatches `documents.process` (`materials.py:166`). The Materials tab polls status and surfaces queued/processing/ready/failed with retry and evidence preview (`Materials.jsx:21-171`). Processing parses per-page text with OCR fallback (`pdf_parser.py:35-54`), clears prior chunks for idempotent retry, chunks at 1000/150, embeds with Gemini 768-d, and chains concept extraction (`document_tasks.py:27-88`). Empty extractions honestly become `failed`, never fake `ready`. The Tutor turn (`tutor.py:206-267`) classifies intent, retrieves top-5 chunks strictly filtered by `project_id`, grades evidence, and either generates a paraphrased cited answer or refuses with a fixed message; citations are normalized to `{pdf_name, page_number, chunk_excerpt}` and matched to cited pages with fallback to all chunks. Conversations are first-class (create/rename/delete/deep-link in `AITutor.jsx:117-172`), memory combines rolling summaries, typed learner facts, and assessment stats without shipping whole history. Quiz start requires concepts (`quiz_flat.py:120-122`), generates an MCQ/open mix in Celery (`quiz_tasks.py:240-286`), saves drafts without grading, then submit grades everything: tolerant MCQ match plus one-sentence LLM explanation, strict LLM open-ended judging with blank=0 guards, then per-question 70/30 mastery updates plus history snapshots before marking `completed`. Results reveal answers only post-completion (`quiz_flat.py:306-327`). Mastery and growth read live `Concept.mastery_level` plus `MasteryHistory`; the Concepts tab, project Analytics (growth cards, series chart, needs-attention), Home (next action, loop stages), and Global analytics all consume the same derived data, so steps genuinely pass data rather than rendering independently. Recommendations are the loop's weak link: computed inline from weak concepts, missing docs, failed quizzes, and growth trends (`analytics.py:468-529`), never persisted. Admin covers the required nine areas with filters and per-user journey inspection.

## 4. AI/RAG evaluation (~400 words)

Chat provider is Inception Labs Mercury (`INCEPTION_MODEL_DEFAULT = "mercury-2.5"` in `ai/llm.py:8-30`) via OpenAI-compatible `ChatOpenAI`, with Groq retained as commented standby and a `FakeMessagesListChatModel` fallback when no key is set; every call passes through `TrackedLLM`, which meters provider, model, tokens, latency, and cost (`ai_usage_service.py:238-283`). Embeddings are Gemini `gemini-embedding-001` at 768 dimensions in both ingest (`document_tasks.py:35`) and retrieval (`tutor_nodes.py:352-356`, `quiz_nodes.py:43-47`), matching `Vector(768)` (`document.py:27`), so dimensionality is consistent. The RAG pipeline is extraction → 1000/150 chunking → embedding → project-filtered pgvector cosine top-5 → LLM evidence grade → constrained generation → citation matching, and the same retrieval grounds quiz generation (`quiz_nodes.py:40-60,81-117`). Grounding is structural, not cosmetic: retrieval filters by `project_id` at the SQL level, the grader routes insufficient evidence to `reject_answer` (`tutor_graph.py:26-31`), and the generation prompt forbids verbatim copying while requiring `[Source: Page N]` per claim. Failure handling is reasonable but uneven: the grader fails open (provider outage degrades to attempted answer rather than 500), provider errors map to 429/502 (`tutor.py:29-54`), quiz/grading/concept tasks retry 2–3 times with strict JSON re-parsing, but the tutor turn itself has no per-node retry or timeout (README admits this). Structured outputs are validated throughout: `SelectorDecision`, `GeneratedQuestion`, `EvaluatorVerdict`, `MCQQuestion`, `ConceptExtraction`, `OpenEndedEvaluation`, and `ChatMasterySignal` all gate persistence. Quiz scoring is deterministic for MCQ and LLM-judged for open-ended with blank-answer hardening. Suggestion chips are genuinely constrained: generated only from concepts plus conversation text with programmatic novelty, diversity, length, and vocabulary-overlap gates (`tutor_nodes.py:158-202`). The main reservations are that quick-action "tools" are prompt directives rather than authorized tool calls, and suggestion/grading quality ultimately depends on provider behavior, which is observed (AI usage + evaluations) but has no automated regression suite.

## 5. Mastery/recommendation evaluation (~250 words)

Mastery math is documented and live: every quiz question moves its concept `old*0.7 + score*0.3` (`quiz_tasks.py:146`), tutor-detected understanding applies the same blend with a confidence score (`concept_tasks.py:124`), and each update appends an idempotent `MasteryHistory` row with a lazily inserted baseline so growth has an honest origin (`analytics_service.py:134-171`). Growth is pure, tested math: point deltas, ±5 pt trend thresholds, 4-observation recent window, carry-forward series without invented interpolation. No mastery value is hardcoded or random; the only static numbers are display thresholds (70/40). The previously reported "quiz completed → mastery updated → zero recommendation rows" is confirmed as **structural, not a regression**: there is no recommendations table in the codebase (grep finds only the `Recommendation` Pydantic schema in `schemas/mastery.py:67-69` and inline dicts in `analytics.py`), so zero rows is the expected outcome of a design where recommendations are computed on read. The quiz→mastery→history links in the chain do work (`quiz_tasks.py:332-341` drives `update_mastery_from_quiz_task` per question, which calls `record_mastery_snapshot`). What does not exist is any persisted LLM-personalized recommendation: `mastery_engine.recommend_next` is decorated and functional but reachable only via legacy `GET /recommendations`, which the frontend never calls, while the UI surfaces rule-based inline lists. The Recommendations page "not found" has the same root cause family but is distinct: no such route, tab, or nav entry ever existed (`App.jsx:73-95`, `tabs.js:7-14`), so it is a missing-page outcome of the no-persistence design rather than a routing bug.

## 6. Data model & security findings (~350 words)

Schema covers users, spaces, projects, documents/chunks, sessions/messages, concepts, quizzes/questions, assignments/submissions, dual mastery stores, mastery history, learning context/summaries, and AI usage with FKs, indexes, and unique constraints (`assessment.py`, `mastery.py:57-59`, `learning.py:46-53`); gaps are the absent recommendations and events tables (`event.py` is empty). `overall_progress` is a stale column nothing recomputes (`docs/MASTERY.md:122-129`).

### Data isolation

Ownership is enforced server-side on every route family: spaces (`deps.py:38-48`), nested projects (`deps.py:50-65`), flat project/quiz access via parent-space owner (`deps.py:67-98`), conversations scoped to project with 404-masking (`tutor.py:119-130`), documents by project (`materials.py:38-58`), and analytics scoping to owned projects (`analytics.py:53-68`). Retrieval filters `DocumentChunk.project_id` at SQL level in both tutor and quiz paths, conversation summaries are re-scoped to the requesting project (`tutor_nodes.py:485-496`), and background tasks propagate project/user IDs rather than trusting client claims. No cross-user query path was found. Limitation: verified statically only, since the sandbox has no two accounts for a live IDOR probe.

Remaining findings: auth uses bcrypt with JWT Bearer (`security.py:6-22`); email validation is strict server-side (`schemas/user.py:5-18`); upload enforces PDF type plus hash/name dedupe; ORM usage keeps SQL injection risk low. Weaknesses: `ADMIN_EMAIL/PASSWORD/NAME` seed defaults to a trivial password (`config.py:49-52`, `admin_seed.py:20-58`); JWT expiry is 7 days with no refresh/rotation (`config.py:20`); passwords over 72 bytes are silently truncated before bcrypt (`security.py:13-16`); upload `safe_name` concatenates the raw client filename without `basename` sanitization (`materials.py:110-111`); no rate limiting anywhere; prompt-injection defense rests on grounding/validation gates (`learning_tasks.py:183-203`, generation constraints) rather than a data/instruction boundary. No committed secrets: `.env` is git-ignored, no `.env` file is tracked, and the historical LangSmith key in `prompt.md` is already redacted; live keys exist only as variable names in the local `.env` (types: DB URL, JWT secret, Inception/Google/LangSmith/Redis/OCR keys), values never extracted.

## 7. Document processing evaluation (~200 words)

Upload → `queued` → Celery `documents.process` → `processing` → parse → idempotent chunk clear → split → embed → index → `ready`, with any exception rolling back to `failed` (`document_tasks.py:13-88`), matches the spec pipeline. Retry re-queues and re-dispatches (`materials.py:61-75`); Celery retries (3 for concepts, 2–3 for quiz tasks) plus unique constraints give duplicate-safe reprocessing. Corrupt PDFs fall into `failed` via the exception path; textless PDFs become `failed` with an explicit message instead of fake readiness (`document_tasks.py:51-59`); scanned pages get Tesseract OCR fallback per page with per-page failure isolation (`pdf_parser.py:17-54`), and the Dockerfile installs the OCR binary (`backend/Dockerfile`). Large files are protected during upload by 1 MB chunked writes (`materials.py:113-121`), though embedding batches whole chunk lists in one call and very large documents could stress memory. Duplicate uploads are rejected by content hash and filename (409). Concept extraction follows automatically on success with validation, generic-term filtering, and semantic dedupe. Missing: no file-size cap, no MIME sniffing beyond extension/content-type, no per-page count guard, and no dead-letter/visibility beyond status strings surfaced in admin jobs.
